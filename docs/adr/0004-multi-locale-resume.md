# Multi-locale Resume — shared structure with per-locale text

The Resume Builder needs to export the CV in both English and Spanish, and the user wants to keep both versions in sync as they edit. Three properties are non-negotiable: (a) editing either locale is valid (peer-mode, not single-source), (b) structural changes (adding/removing/reordering Sections or Items) propagate to both locales instantly, (c) text edits in one locale auto-translate to the other on field blur, with a stale marker if translation fails.

We're modeling this as **shared structure + per-locale text**: each locale lives in its own file on disk with the full `Resume` shape, but most of the data (every `id`, ordering, `section.type`, `hidden`, all dates, `Header`, organization/institution names, tech stacks, skill tags) is constrained to be **identical** across files. Only a curated set of `Translatable field`s — section titles, item subtitles, descriptions, link labels, category names, and Showcase item titles — differs between locales. Translation between locales runs through **DeepL API Free** invoked from the Hono backend on field blur.

## Considered options

- **Single-source-of-truth (EN primary, ES derived, regenerated on demand)** — rejected. The user explicitly wants `viceversa` editing; deriving ES from EN locks them out of editing in Spanish directly. Would also need a "regenerate" flow with overwrite warnings.
- **Inline per-field locale variants (`title`, `title_es` on every translatable field of the existing `Resume` type)** — rejected. Pollutes the type with locale knowledge at the leaf level, makes the field-classification (translatable vs shared) implicit in the field name suffix instead of explicit in a single registry, and breaks the parallel between `src/preview/` and `src/pdf/` renderers (they'd both have to know which suffix to read).
- **Two fully independent `Resume` documents (one per locale, no shared-structure invariant)** — rejected. Structural drift (different IDs, different section ordering, "I added an item in EN but forgot in ES") would be unbearable for the use case. Two PDFs that don't share an outline are worse than no Spanish PDF.
- **Shared structure + per-locale text (this ADR)** — chosen. The `Resume` type itself stays unchanged; the multi-locale envelope wraps it (`{ schemaVersion, locales: { en: Resume, es: Resume } }`). Edits are dispatched in the store via two distinct actions — one writes only the active locale (translatable edits), the other writes both locales (structural/shared edits). DeepL is invoked on field blur from the backend, where the API key lives.
- **Translation provider: LibreTranslate self-hosted vs DeepL API Free vs Google Translate API** — chose DeepL for EN↔ES quality (visibly better than LibreTranslate for prose, comparable to Google) and free-tier generosity (500k chars/month, more than enough for a personal CV editor). LibreTranslate self-hosted is the documented fallback if DeepL's credit-card-for-verification requirement becomes a blocker.

## Consequences

- **Field classification is load-bearing.** A single registry decides whether each editable field is `Shared` or `Translatable`. Bugs in the registry directly cause data inconsistency — e.g., classifying `TimelineItem.title` as `Translatable` would translate "Adia Health" to "Salud Adia", breaking the proper-noun invariant. The registry lives close to the types and is reviewed when adding a new section type.
- **Two save paths.** The store gains `setResumeActiveLocale(producer)` and `setResumeBothLocales(producer)`. Existing `setResume` call sites are migrated to one or the other based on what they touch. Form-field `onChange` handlers and Sidebar structural ops (DnD, add/remove, hidden toggle, header edits) are the two call-site clusters.
- **Auto-bootstrap of `resume_es.json`.** On first read, if the Spanish file is missing, the backend translates the English file end-to-end via DeepL and writes the result. This is a one-time cost; subsequent reads return both files as-is.
- **Stale tracking is per-field, hash-based.** Each locale stores, alongside each translatable field's value, the hash of the source text it was translated from. When the source is edited and translation succeeds, both the value and the source-hash update. When translation fails, only the source updates — the hash divergence marks the other locale's field as stale, surfaced as a ⚠ in the UI with a manual retry.
- **Last-write-wins.** If the user edits the same translatable field on both locales before the network roundtrip resolves, the backend's translation response will overwrite the manual edit. Documented behavior, not a bug.
- **Backend env var: `DEEPL_API_KEY`.** Required for translation; absent → translation endpoint returns 503 and the frontend leaves fields stale. Configured via Render env vars (see [`render.yaml`](../../render.yaml)).
- **PDF export bundles both locales as a ZIP.** A single "Export PDF" button generates `EmanuelRodriguezBedeman.pdf` (EN) and `EmanuelRodriguezBedeman_es.pdf` (ES) and ships them as `EmanuelRodriguezBedeman_resumes.zip` via `jszip`. The active-locale toggle does not change export behavior — exports are always both, so the user never has to remember to switch and re-export.
- **`data/resume.json` is renamed to `data/resume_en.json`.** One-time migration. The data is unchanged; only the filename changes for symmetry with `resume_es.json`.
